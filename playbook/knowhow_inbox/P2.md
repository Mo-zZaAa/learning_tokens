# P2(다듬기 담당, Ondo, Dinari, 야간 ATS 3곳, 전체 그림) 새 교훈

## 쓰기 교훈
1. "쉽게 말하면"과 "주장"을 같은 문장으로 두지 않는다. 쉽게 말하면은 풀어 쓴 한 줄, 주장은 숫자와 근거가 든 판단 한 줄. 두 줄이 같으면 독자는 한 줄을 건너뛴다.
2. 기간이 다른 값을 한 줄에서 비교하지 않는다(분기 15.0%와 최근 3주 29.8%). 집계 주체가 다른 값도 이어 붙이지 않는다(회사 TVL 대 rwa.xyz 발행 잔액, 회사 발표 체결대금 대 FINRA 주간 보고). 둘 다 쓰되 "이어 붙이지 않음"을 줄에 적는다.
3. "지표가 달라 비교 못 함"이라고 쓰기 전에 DB의 "무엇을 잰 것" 칸으로 실제 지표 이름을 확인한다. Ondo의 국채 표와 주식 표는 둘 다 분산 가치(Total Value)였다. 근거 없는 "다르다"는 독자를 더 헷갈리게 한다.
4. 한 줄에 "(회사 주장)", "(보도)" 표시가 붙은 큰 그림은 같은 사업의 제3자 순위와 괴리가 나면 이어 읽지 않도록 줄을 분리한다(Ondo 2026-05 TVL 10억 달러 주장 대 2026-11 rwa.xyz 8.99억 달러).
5. KSF로 쓸 근거가 부족하면 첫 줄에 "KSF로 볼 만한 근거는 부족함"이라고 쓰고 사실은 세부 불렛으로 남긴다(MOON). 억지로 성공 요인으로 쓰지 않는다.
6. "큰 곳은 X. 그래서 Y"는 독자가 "큰 곳이 뭔데"라고 묻는다. "방향은 X, 실행은 Y"로 쓴다.
7. 숫자 범위도 물결표를 쓰지 않는다. "5%에서 10%", "0.2달러에서 50달러". 시간대(밤 8시~새벽 4시), 기간(2026-10-12~30)만 물결.
8. 용어 뜻 줄을 처음 나오는 대분류 맨 위에 둔다. 뜻이 본문 한참 아래에 있으면(분산 가치, 합성형, 보관형, FMA, MOU) 앞 줄을 읽는 독자가 이미 막힌다.
9. 우리 분류 이름(보관형, 합성형, 연계증권, 직접, 인수, 제휴, 위탁)은 쓸 때마다 뜻 줄 한 번. 방법 구분 표기(줄 끝 직접, 인수)는 "자산" 대분류 아래에 뜻 줄을 둔다.
10. 이전 이름이 있는 상품(Ondo Stocks의 옛 이름 Ondo Global Markets)은 처음 나오는 줄에서 이름이 둘인 이유를 뜻 줄로 쓴다. 발행 법인명에 옛 이름이 남아 있으면 같이.
11. 한 회사 안에서 서로 어긋나 보이는 두 사실(Dinari 미국판 대상이 개인인지 적격 투자자인지)은 하나로 고르지 말고 "두 서술이 같은 상품의 다른 경로인지는 확인하지 못함"으로 둘 다 쓴다.

## 작업 방식 교훈
12. 줄 ID: 대분류 첫머리의 "주장 :" 줄은 전체 그림이 {xx-0000}으로 링크한다. 길게 고쳐 쓰면 유사도 0.55 아래로 떨어져 ID가 끊긴다. 설명은 세부 불렛으로 내리거나, 늘렸다면 `python3 web/build.py` 뒤 web/line_ids.json에서 옛 ID의 text를 새 문구로 바꾸고 새로 생긴 ID 항목을 지운다(scratchpad remap 스크립트와 같은 방식). build의 "찾지 못한 줄 링크" 경고로 확인.
13. 큰 그림 빈칸 찾기: db/facts.csv에서 검증 상태가 단일 출처, 사용자 제공, 교차 확인, 회사 주장이면서 본문에 번호가 안 쓰인 사실을 회사별로 뽑아 본다(본문의 F 번호 집합을 빼는 짧은 파이썬). 출처 규칙 완화 뒤에는 여기서 창업 배경, 사고 원인, 한국 비중, 파트너 거래대금, 병행 MOU가 나왔다.
14. 여러 담당이 같은 저장소를 동시에 고치면 중간 커밋이 생겨 git HEAD가 "작업 전 상태"가 아니게 된다. 줄 ID 복구처럼 이전 상태가 필요한 일은 작업 시작 전에 본문과 web/line_ids.json 사본을 떠 둔다.
15. web/line_ids.json은 모든 담당이 build로 같이 쓴다. 복구 스크립트는 읽고 바로 쓰는 짧은 구간만 두고 자기 접두(on, dn, bo, br, mo)만 고친다.
