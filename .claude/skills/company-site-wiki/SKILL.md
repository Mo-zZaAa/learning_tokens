# 공식 사이트 전수 조사와 LLM 위키 정리

## 왜 이 절차인가

검색과 몇 번의 페이지 열람으로 조사하면 "전체 목록"이 없어서 무엇을 안 봤는지 모른다. 그래서 순서를 바꾼다.

1. 읽기 전에 장부부터 만든다. 사이트의 모든 URL을 `inventory.csv` 한 파일에 올리고, URL마다 계획(read, skim, list, skip)과 처리 상태를 남긴다.
2. 읽은 것은 3층으로 쌓는다. raw(원문 변환본, 손대지 않음) > notes(묶음별 사실 메모) > wiki(주제별 정리). Karpathy의 LLM Wiki 패턴을 기업 조사용으로 맞춘 것이다.
3. 마지막에 장부와 위키를 대조한다. 정독한 페이지가 위키 어디에도 출처로 안 쓰였으면 누락 후보로 뜬다.

## 역할 나누기: 토큰을 아끼는 핵심

비싼 모델이 원문을 직접 읽지 않게 한다. 일은 세 층으로 나눈다.

| 층 | 누가 | 하는 일 | 드는 것 |
|---|---|---|---|
| 수집 | 스크립트 | 목록화, 수집, 변환, 묶음 생성, 검수, 점검 | 토큰 없음 |
| 읽기 | 값싼 모델(Haiku 등) | 스크립트 실행, 묶음을 읽고 정해진 형식의 사실 메모 작성 | 값싼 토큰 |
| 정리 | 똑똑한 모델 | 읽기 계획 확정, 메모만 읽고 위키와 최종 산출물 작성, 핵심 주장만 원문 대조 | 원문의 5~10% 분량 |

값싼 모델이 쓴 메모는 그대로 믿지 않는다. 메모의 모든 사실에는 원문에서 글자 그대로 복사한 근거 구절을 붙이게 하고, `verify` 명령이 그 구절이 원문에 실제로 있는지 기계적으로 대조한다. 지어낸 내용은 여기서 걸린다.

세션 전체를 값싼 모델로 돌려도 된다. 그때는 5단계(메모)와 검수까지 하고 멈춘 뒤, notes와 `verify.md`, `coverage.md`를 똑똑한 모델에게 넘긴다. 서브에이전트를 쓸 수 있으면 `agents/` 폴더의 site-collector와 site-pack-reader(둘 다 Haiku 지정)를 쓴다.

## 준비

- 필요한 것: python3, `requests beautifulsoup4 lxml markdownify playwright`, PDF 변환용 `markitdown[pdf]`(선택). 없으면 `pip install`로 설치. 브라우저는 설치된 Chrome을 먼저 쓰고, 없으면 `playwright install chromium`.
- 스크립트: 이 스킬 폴더의 `scripts/sitewiki.py`. 실행 전 `python scripts/sitewiki.py --help`가 도는지 확인.
- 작업 폴더: 회사마다 하나(`work/<회사>`). 모든 명령은 이어서 다시 실행할 수 있다. 중간에 끊겨도 장부에 상태가 남는다.
- 셸에서 대상 사이트에 접속되는지 먼저 확인(`curl -sI https://대상`). 접속이 막힌 환경이면 "막혔을 때" 절을 따른다.
- `inventory.csv`, raw, packs를 통째로 대화에 올리지 않는다. 현황은 `plan_summary.md`, `packs/_index.md`, `packs/_groups.md`, `verify.md`, `coverage.md`로 본다.

## 절차

### 0. 범위와 조사 질문 정하기 (똑똑한 모델)

회사명, 대표 도메인, 이미 아는 하위 사이트, 그리고 위키가 답해야 할 조사 질문을 적는다. 질문이 따로 없으면 기본 질문을 쓴다: 무엇을 파는가, 누구에게 파는가, 어떤 구조로 하는가(법인, 인허가, 파트너, 인프라), 가격과 이용 조건, 제공 지역과 제한, 최근 변화. 조사 질문은 읽기 담당에게 그대로 전달한다.

### 1. 전수 목록화 map (스크립트)

```bash
python scripts/sitewiki.py map --work work/<회사> --domain example.com --seed https://www.example.com
```

하는 일: robots.txt와 사이트맵(중첩 포함) 읽기, 첫 화면을 실제 브라우저로 열어 메뉴를 펼치고 링크 수집, 링크에서 발견된 하위 호스트 따라가기, 인증서 공개 기록(crt.sh)에서 하위 사이트 후보 찾기. 결과는 `inventory.csv`, `map_log.md`, `plan_summary.md`.

`map_log.md`에서 볼 것(똑똑한 모델이 판단):
- "아직 훑지 않은 하위 사이트 후보": 공개용으로 보이는 것(docs, app, blog, help 등)은 `--seed`로 추가해 map을 다시 실행. 시험용이나 내부용으로 보이는 호스트는 스크립트가 건드리지 않는다. 직접 추가하지도 않는다.
- "사이트가 링크한 외부 호스트": 다른 도메인이지만 회사 소유인 곳을 가려낸다. 근거(푸터의 법인명, 자동 이동, 약관의 운영 주체)가 있으면 `--domain 새도메인 --seed https://새도메인`으로 같은 작업 폴더에 map을 추가 실행.
- "(주의) 상한에 걸려 못 연 사이트맵 파일": 있으면 `--sitemap-cap`을 올려 재실행할지 판단.

### 2. 읽기 계획 plan (똑똑한 모델이 한 번 확정)

| 값 | 뜻 | 드는 것 |
|---|---|---|
| read | 수집하고 정독 | 수집 시간과 읽기 토큰 |
| skim | 수집하되 제목과 첫머리만 표로 확인 | 수집 시간, 토큰 조금 |
| list | URL만 장부에 남김 | 없음 |
| skip | 수집 안 함(언어판 중복, robots 제외, 수동 제외) | 없음 |

스크립트의 기본 규칙: 언어판과 국가판 중복은 한 벌만 남김, 같은 경로 틀로 40쪽 넘게 반복되는 묶음은 표본 5쪽만 read 나머지는 skim과 list, 300쪽 이하 작은 사이트는 전부 read.

조정은 URL 패턴으로 한다. 여러 패턴에 걸리면 list < skim < read < skip 순으로 뒤쪽이 우선이고, 지정은 `overrides.json`에 남는다.

```bash
python scripts/sitewiki.py plan --work work/<회사> \
  --skip 'https://app.example.com/*' --list 'https://www.example.com/prices/*' \
  --skim 'https://www.example.com/legal/*' --read 'https://blog.example.com/*tokeniz*'
```

조정 기준:
- 앱 화면, 로그인, 검색 결과, 문의 양식은 skip.
- 종목별, 자산별, 국가별로 같은 틀이 반복되는 페이지는 표본만 read, 나머지는 list.
- 블로그, 보도자료, 약관, 고객센터 글처럼 글마다 내용이 다른 묶음은 표본 규칙이 맞지 않는다. 먼저 `inventory.csv`의 URL을 조사 질문의 핵심어로 걸러(`grep -iE`) 걸린 것만 skim이나 read로 올린다. 토큰이 들지 않는 선별이다.
- 대상 도메인 밖에 올려 둔 문서(다른 회사 서버의 투자설명서 PDF 등)는 `plan --add 'https://주소'`로 낱개 추가한다.
- 정독 대상이 300쪽을 넘으면 `plan_summary.md`와 추천 범위를 사용자에게 보여 주고 진행한다.

### 3. 수집과 변환 fetch (스크립트)

```bash
python scripts/sitewiki.py fetch --work work/<회사> --minutes 8
```

"대기"가 0이 될 때까지 같은 명령을 반복한다. 속도는 정적 수집 쪽당 1초 안팎, 브라우저로 여는 쪽은 10초 안팎.

하는 일:
- 정적 요청으로 먼저 받는다. 정독 대상이면서 경로가 얕은 페이지(첫 화면, 구역 첫 화면, 상품 페이지), 탭이나 더보기가 있는 페이지, 내용이 빈 페이지는 브라우저로 다시 연다.
- 브라우저에서는 끝까지 스크롤한 뒤 눌러 본다. 표준 방식의 탭, 아코디언, 더보기는 물론, 표시 없이 만든 누르는 카드와 전환 버튼(손가락 커서가 뜨는 요소)도 누른다. 첫 화면에서는 상단 메뉴에 마우스를 올려 펼친다.
- 본문은 처음 열었을 때의 화면이다. 누른 뒤 새로 보인 내용은 각 파일의 "펼치거나 눌러야 보이던 내용" 절에 "### <누른 것> 누른 뒤" 덩어리로 붙는다. 값만 바뀌는 칸은 항목 이름과 함께 남는다(예: 상품 카드를 누르면 바뀌는 TVL, APY, Price). 이용 제한과 면책 문구가 이 절에 자주 있다.
- 눌렀더니 다른 페이지로 넘어가면 그 주소를 장부에 추가하고 돌아온다. 사이트맵에 없는 페이지가 이렇게 잡힌다. 페이지 안의 내부 링크도 모두 장부에 추가되어 이어서 수집된다.
- PDF는 내려받아 마크다운으로 바꾼다.

받지 못하는 것: 그래프 안의 점별 값(글자가 아니라 그림), 마우스를 올려야 뜨는 풍선말(상단 메뉴는 예외), 값을 입력해야 결과가 나오는 계산기와 검색, 로그인이나 지갑 연결 뒤 화면, 한 화면에서 30개를 넘는 누르는 요소. 조사에 꼭 필요하면 그 화면만 브라우저 도구로 직접 열어 확인하고 notes에 적는다.

옵션: 특정 구역만 먼저 받으려면 `--only 'URL패턴'`. 정독 대상을 전부 브라우저로 열려면 `--render read`. 이미 받은 페이지를 다시 받으려면 `--refetch 'URL패턴'`. 표준 방식만 누르려면 `--click basic`. 상태 값: ok, thin(내용 거의 없음), gone(404), blocked(차단), nonhtml, error.

### 4. 읽기 묶음 digest (스크립트)

```bash
python scripts/sitewiki.py digest --work work/<회사>
```

- `packs/_index.md`: 묶음 파일 목록(호스트와 구역별, 12만 자 단위)과 글자수. 읽을 묶음을 고르는 표로 쓴다. 글자수를 4로 나누면 대략의 토큰 수다.
- `packs/_groups.md`: 큰 묶음마다 "서로 닮은 정도". 0.5 이상이면 같은 틀이라 표본으로 충분, 0.25 미만이면 글마다 다르니 제목을 보고 관련 글을 read로 올린다. 올린 뒤에는 fetch와 digest를 다시 실행.

똑똑한 모델은 `_index.md`의 묶음 이름과 글자수만 보고 읽을 묶음을 고른다. 묶음 내용은 열지 않는다.

### 5. 읽기와 메모 notes (값싼 모델)

묶음 하나마다 `notes/<묶음 파일명>`을 하나 쓴다. 파일명은 묶음과 똑같이 한다(검수가 이름으로 짝을 맞춘다). 서브에이전트를 쓸 수 있으면 묶음 하나당 site-pack-reader 하나를 부르고, 묶음 경로와 조사 질문을 넘긴다. 동시에 4~6개까지 돌린다. 읽기 담당은 영수증(파일 경로, 페이지 수, 사실 수)만 돌려주고 원문이나 메모 내용을 대화로 돌려보내지 않는다.

메모 형식(이 형식을 지켜야 검수가 된다):

```markdown
# notes: <묶음 파일명>

## https://페이지-주소
- [상품] 사실을 한국어 한 문장으로. 숫자와 고유명사는 원문 표기 그대로
  근거: "원문에서 글자 그대로 복사한 5~15단어"
- [지역제한] 사실 한 문장
  근거: "원문 그대로"
- 관련도: 높음

## https://다음-페이지-주소
- 해당 없음: 행사 안내

## 승격 후보
- https://훑기-표에서-조사-질문과-관련-있어-보이는-주소
```

분류표는 이 가운데 하나만 쓴다: 상품, 구조, 인허가, 수수료, 지역제한, 고객, 파트너, 숫자, 연혁, 용어, 기타.

메모 쓰는 규칙:
1. 묶음의 `<<<PAGE 주소>>>`마다 `## 주소` 절을 하나씩 만든다. 한 쪽도 빠뜨리지 않는다. 쓸 내용이 없으면 "해당 없음: 사유" 한 줄.
2. 사실마다 바로 아래 줄에 근거를 붙인다. 근거는 원문에서 글자 그대로 복사한다. 번역하거나 고치거나 이어 붙이지 않는다. 중간을 줄일 때만 `...`을 쓴다.
3. 원문에 없는 내용, 추측, 평가, 배경 지식을 쓰지 않는다. 확실하지 않으면 쓰지 않는다.
4. 숫자, 날짜, 회사명, 상품명, 법인명, 인허가 이름은 원문 표기 그대로 적는다.
5. "펼치거나 눌러야 보이던 내용" 절과 "구조화 데이터" 절도 읽는다. 눌러서 나온 값은 무엇을 눌렀을 때의 값인지 함께 적는다.
6. 여러 페이지에 똑같이 반복되는 문구(공통 면책 문구, 메뉴)는 처음 나온 페이지에만 적는다.
7. 한 페이지에 사실은 많아야 15줄. 조사 질문과 무관한 내용은 적지 않는다.
8. 묶음 끝의 훑기 표(URL, 제목, 첫머리)에서 조사 질문과 관련 있어 보이는 주소는 "## 승격 후보"에 주소만 나열한다.

메모가 끝나면 검수한다(스크립트).

```bash
python scripts/sitewiki.py verify --work work/<회사>
```

`verify.md`에 메모 파일별 페이지 수와 근거 줄 수, "메모에 빠진 페이지", "원문에서 못 찾은 근거"가 나온다. 빠진 페이지가 있으면 그 묶음을 읽기 담당에게 다시 맡긴다. 근거를 못 찾은 사실은 쓰지 않거나, 꼭 필요하면 그 페이지의 raw 파일만 열어 확인한다.

토큰 예산이 정해져 있으면 관련도 높은 묶음만 읽고, 안 읽은 묶음은 coverage에 "미열람"으로 남긴다. 읽지 않은 것을 읽은 것처럼 쓰지 않는다.

### 6. 위키 작성 wiki (똑똑한 모델)

읽는 것은 notes와 `verify.md`뿐이다. 묶음과 raw는 열지 않는다. 예외는 두 가지다: 인허가, 수수료, 숫자처럼 결론에 직접 쓰는 핵심 주장은 `grep`으로 raw의 해당 줄만 확인한다. 메모끼리 어긋나면 해당 페이지의 raw 파일만 연다.

```
wiki/
  index.md           전체 목차와 페이지별 한 줄 요약
  overview.md        회사 한눈에: 하는 일, 사업 구조, 법인과 브랜드, 주요 숫자
  products/<이름>.md  상품과 서비스별: 무엇인지, 대상 고객, 이용 조건, 수수료, 제공 지역, 구조(누가 발행, 보관, 체결하는지)
  licenses.md        인허가와 규제: 법인별 라이선스, 관할, 제한 지역
  fees.md            수수료와 가격
  partners.md        파트너, 인수한 회사, 외부 인프라
  timeline.md        연혁과 발표(날짜순)
  glossary.md        사이트에 나온 용어를 쉬운 말로, 용어 사이 관계 포함
  site-map.md        호스트와 구역별로 무엇이 있는지(다음 조사 때 볼 곳)
  open-questions.md  사이트만으로 확인 안 되는 것, 어긋나는 서술, 외부 확인이 필요한 것
  coverage.md        수집과 반영 점검표, 반영하지 않은 페이지와 사유
  log.md             작업 기록(날짜, 수집 범위, 고친 것)
```

작성 규칙:
- 사실 한 줄마다 출처 URL을 붙인다: `- 내용 [출처](URL)`. 페이지 맨 위에 확인한 날짜를 적는다.
- 공식 사이트 내용은 "회사가 밝힌 내용"이다. 인허가, 규모, 순위처럼 제3자 확인이 필요한 주장은 그대로 사실로 쓰지 않고 open-questions.md에 확인할 곳(감독기관 등록부 등)과 함께 올린다.
- 사실과 해석을 섞지 않는다. 해석은 각 페이지 맨 아래 "해석" 절에 따로 둔다.
- 원문은 자기 말로 요약한다. 인용은 표현 자체가 중요할 때만 짧게 쓴다. raw 원문 묶음은 내부 작업용이고, 밖으로 나가는 산출물에는 요약과 출처 링크만 쓴다.
- 날짜가 있는 정보는 날짜를 함께 적는다. 사이트 안에서 서로 다른 숫자가 나오면 둘 다 적고 출처를 붙인다.

### 7. 누락 점검 audit (스크립트)

```bash
python scripts/sitewiki.py audit --work work/<회사> --wiki work/<회사>/wiki
```

`coverage.md`에 수집 대기, 차단, 오류, 내용 없음, 그리고 "정독했으나 위키 어디에도 출처로 안 쓰인 페이지"가 나온다. 마지막 목록의 각 페이지는 위키에 반영하거나, wiki/coverage.md의 "읽었으나 반영하지 않은 페이지" 아래에 URL과 사유를 적는다(메모에 "해당 없음"으로 적힌 페이지는 그 사유를 그대로 옮긴다). 계획이 list나 skip이라 안 읽은 범위는 구역과 쪽수를 그대로 밝힌다.

### 8. 전달과 보관

- 위키 폴더와 notes, `inventory.csv`, `verify.md`, `coverage.md`를 전달한다. 프로젝트가 연결된 대화라면 위키 페이지를 프로젝트 문서로도 저장한다.
- 작업 폴더(장부와 raw)는 다음 대화로 넘어가지 않을 수 있다. 다시 쓸 일이 있으면 zip으로 묶어 사용자에게 준다.
- 나중에 갱신할 때는 이전 작업 폴더를 그대로 두고 map을 다시 실행한다. 새 URL만 대기 상태로 추가된다.

## 지킬 것

- robots.txt가 막은 경로는 수집하지 않는다(스크립트가 자동으로 뺀다). 로그인이 필요한 화면, 캡차, 차단은 우회하지 않는다.
- 요청 속도를 올리지 않는다(기본: 동시 4건, 묶음 사이 1초).
- 공개용이 아닌 호스트(staging, dev, test, internal, admin 등)는 열지 않는다.

## 막혔을 때

- 상태가 blocked인 페이지: WebFetch 같은 다른 정식 열람 도구로 그 URL만 다시 시도한다. 그래도 안 되면 coverage에 "미열람(차단)"으로 남기고, 필요하면 사용자에게 직접 열어 달라고 한다.
- 셸에서 사이트 접속 자체가 막힌 환경: 스크립트를 쓸 수 없다. 사용자 컴퓨터(Claude Code 등)에서 이 스크립트를 돌려 작업 폴더를 받아 오거나, robots.txt와 사이트맵을 웹 열람 도구로 읽어 같은 형식의 장부를 손으로 만들고 5단계부터 같은 방식으로 진행한다.
- 브라우저 실행 실패: `--render never`로 정적 수집만 먼저 하고, thin으로 남은 페이지만 따로 처리한다.
- 수집이 너무 오래 걸림: `plan`의 `--skim-cap`을 낮추고, 글 묶음은 핵심어로 걸러 올리는 방식으로 바꾼다. 누르기가 오래 걸리는 구역은 `--click basic`으로 받는다.
