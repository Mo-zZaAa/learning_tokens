# 공식 사이트 전수 조사와 LLM 위키 정리

## 왜 이 절차인가

검색과 몇 번의 페이지 열람으로 조사하면 "전체 목록"이 없어서 무엇을 안 봤는지 모른다. 그래서 순서를 바꾼다.

1. 읽기 전에 장부부터 만든다. 사이트의 모든 URL을 `inventory.csv` 한 파일에 올리고, URL마다 계획(read, skim, list, skip)과 처리 상태를 남긴다.
2. 수집과 변환은 스크립트가 한다. 토큰이 들지 않으므로 넓게 수집해도 된다. 토큰은 읽기에서만 든다.
3. 읽은 것은 3층으로 쌓는다. raw(원문 변환본, 손대지 않음) > notes(묶음별 사실 메모) > wiki(주제별 정리). Karpathy의 LLM Wiki 패턴을 기업 조사용으로 맞춘 것이다.
4. 마지막에 장부와 위키를 대조한다. 정독한 페이지가 위키 어디에도 출처로 안 쓰였으면 누락 후보로 뜬다.

## 준비

- 필요한 것: python3, `requests beautifulsoup4 lxml markdownify playwright`, PDF 변환용 `markitdown`(선택). 없으면 `pip install`로 설치. 브라우저는 설치된 Chrome을 먼저 쓰고, 없으면 `playwright install chromium`.
- 스크립트: 이 스킬 폴더의 `scripts/sitewiki.py`. 실행 전 `python3 scripts/sitewiki.py --help`가 도는지 확인.
- 작업 폴더: 회사마다 하나(`work/<회사>`). 모든 명령은 이어서 다시 실행할 수 있다. 중간에 끊겨도 장부에 상태가 남는다.
- 셸에서 대상 사이트에 접속되는지 먼저 확인(`curl -sI https://대상`). 접속이 막힌 환경이면 "막혔을 때" 절을 따른다.

## 절차

### 0. 범위와 조사 질문 정하기

회사명, 대표 도메인, 이미 아는 하위 사이트, 그리고 위키가 답해야 할 조사 질문을 적는다. 질문이 따로 없으면 기본 질문을 쓴다: 무엇을 파는가, 누구에게 파는가, 어떤 구조로 하는가(법인, 인허가, 파트너, 인프라), 가격과 이용 조건, 제공 지역과 제한, 최근 변화. 조사 질문은 뒤에서 무엇을 정독할지 고르는 기준이 된다.

### 1. 전수 목록화 (map)

```bash
python3 scripts/sitewiki.py map --work work/<회사> --domain example.com --seed https://www.example.com
```

하는 일: robots.txt와 사이트맵(중첩 포함) 읽기, 첫 화면을 실제 브라우저로 열어 메뉴에 마우스를 올리고 링크 수집, 링크에서 발견된 하위 호스트 따라가기, 인증서 공개 기록(crt.sh)에서 하위 사이트 후보 찾기. 결과는 `inventory.csv`, `map_log.md`, `plan_summary.md`.

`map_log.md`에서 반드시 볼 것:
- "아직 훑지 않은 하위 사이트 후보": 공개용으로 보이는 것(docs, app, blog, help 등)은 `--seed`로 추가해 map을 다시 실행. 시험용이나 내부용으로 보이는 호스트는 스크립트가 건드리지 않는다. 직접 추가하지도 않는다.
- "사이트가 링크한 외부 호스트": 다른 도메인이지만 회사 소유인 곳(법인명 도메인, 인수한 회사, 상품 전용 도메인)을 가려낸다. 근거(푸터의 법인명, 자동 이동, 약관의 운영 주체)가 있으면 `--domain 새도메인 --seed https://새도메인`으로 같은 작업 폴더에 map을 추가 실행.
- "(주의) 상한에 걸려 못 연 사이트맵 파일": 있으면 `--sitemap-cap`을 올려 재실행할지 판단.

### 2. 읽기 계획 조정 (plan)

계획 값은 네 가지다.

| 값 | 뜻 | 드는 것 |
|---|---|---|
| read | 수집하고 정독 | 수집 시간과 읽기 토큰 |
| skim | 수집하되 제목과 첫머리만 표로 확인 | 수집 시간, 토큰 조금 |
| list | URL만 장부에 남김 | 없음 |
| skip | 수집 안 함(언어판 중복, robots 제외, 수동 제외) | 없음 |

스크립트의 기본 규칙: 언어판과 국가판 중복은 한 벌만 남김, 같은 경로 틀로 40쪽 넘게 반복되는 묶음은 표본 5쪽만 read 나머지는 skim과 list, 300쪽 이하 작은 사이트는 전부 read.

조정은 URL 패턴으로 한다. 여러 패턴에 걸리면 list < skim < read < skip 순으로 뒤쪽이 우선이고, 지정은 `overrides.json`에 남는다.

```bash
python3 scripts/sitewiki.py plan --work work/<회사> \
  --skip 'https://app.example.com/*' --list 'https://www.example.com/prices/*' \
  --skim 'https://www.example.com/legal/*' --read 'https://blog.example.com/*tokeniz*'
```

조정 기준:
- 앱 화면, 로그인, 검색 결과, 문의 양식은 skip.
- 종목별, 자산별, 국가별로 같은 틀이 반복되는 페이지는 표본만 read, 나머지는 list.
- 블로그, 보도자료, 약관, 고객센터 글처럼 글마다 내용이 다른 묶음은 표본 규칙이 맞지 않는다. 먼저 `inventory.csv`의 URL을 조사 질문의 핵심어로 걸러(`grep -iE`) 걸린 것만 skim이나 read로 올린다. 토큰이 들지 않는 선별이다.
- 정독 대상이 300쪽을 넘으면 구역별 계획 표(`plan_summary.md`)와 추천 범위를 사용자에게 보여 주고 진행한다.

### 3. 수집과 변환 (fetch)

```bash
python3 scripts/sitewiki.py fetch --work work/<회사> --minutes 8
```

"대기"가 0이 될 때까지 같은 명령을 반복한다. 속도는 쪽당 1~4초. 하는 일: 정적 요청으로 받고, 내용이 비거나 탭과 더보기 버튼이 있거나 구역 첫 화면이면 브라우저로 다시 열어 스크롤하고 탭, 아코디언, 더보기를 눌러 숨은 내용까지 받는다. 눌러야 보이던 문장은 각 파일의 "펼치거나 눌러야 보이던 내용" 절에 따로 붙는다(이용 제한, 면책 문구가 여기 자주 있다). PDF는 내려받아 마크다운으로 바꾼다. 페이지에서 새로 발견한 내부 링크는 장부에 추가되어 이어서 수집된다. 사이트맵에 없는 페이지가 이 단계에서 잡힌다.

특정 구역만 먼저 받으려면 `--only 'URL패턴'`. 상태 값: ok, thin(내용 거의 없음), gone(404), blocked(차단), nonhtml, error.

### 4. 읽기 묶음 만들기 (digest)

```bash
python3 scripts/sitewiki.py digest --work work/<회사>
```

- `packs/_index.md`: 묶음 파일 목록(호스트와 구역별, 12만 자 단위). 읽기 점검표로 쓴다.
- `packs/_groups.md`: 큰 묶음마다 "서로 닮은 정도". 0.5 이상이면 같은 틀이라 표본으로 충분, 0.25 미만이면 글마다 다르니 제목을 보고 관련 글을 read로 올린다. 올린 뒤에는 fetch와 digest를 다시 실행.

### 5. 읽기와 메모 (notes)

조사 질문과 관련이 큰 묶음부터 읽는다. 읽기로 한 묶음은 끝까지 읽는다(검색어로 일부만 훑지 않는다). 묶음 하나를 읽을 때마다 `notes/<묶음이름>.md`를 쓰고 다음 묶음으로 넘어간다. 메모를 남겨야 뒤에서 원문을 다시 읽지 않는다.

메모 형식:

```markdown
# notes: <묶음 파일명>
## 페이지별 사실
### <URL>
- 사실 한 줄. 표현이 중요한 곳(인허가, 이용 자격, 수수료)은 원문 핵심 표현을 짧게 병기
- 조사 질문 관련도: 높음, 중간, 낮음
### <URL>
- 쓸 내용 없음(사유: 행사 안내)
## 새로 나온 용어
## 서로 어긋나는 서술
## 더 봐야 할 것(수집 안 된 링크, 외부 문서)
```

정독한 페이지는 쓸 내용이 없어도 한 줄을 남긴다. 양이 많고 사용자가 병렬 작업을 원하면 호스트나 구역 단위로 묶음을 나눠 서브에이전트에 맡기고, 각자 같은 형식의 메모만 돌려받는다. 토큰 예산이 정해져 있으면 관련도 높은 묶음만 읽고, 안 읽은 묶음은 coverage에 "미열람"으로 남긴다. 읽지 않은 것을 읽은 것처럼 쓰지 않는다.

### 6. 위키 작성 (wiki)

메모를 주제별로 다시 묶는다. 원문을 다시 열어야 하면 raw 파일을 직접 본다.

```
wiki/
  index.md           전체 목차와 페이지별 한 줄 요약
  overview.md        회사 한눈에: 하는 일, 사업 구조, 법인과 브랜드, 주요 숫자
  products/<이름>.md  상품과 서비스별: 무엇인지, 대상 고객, 이용 조건, 수수료, 제공 지역, 구조(누가 발행, 보관, 체결하는지)
  licenses.md        인허가와 규제: 법인별 라이선스, 관할, 제한 지역
  fees.md            수수료와 가격
  partners.md        파트너, 인수한 회사, 외부 인프라
  timeline.md        연혁과 발표(날짜순)
  glossary.md        사이트에 나온 용어를 쉬운 말로, 용어 사이 관계 포함
  site-map.md        호스트와 구역별로 무엇이 있는지(다음 조사 때 볼 곳)
  open-questions.md  사이트만으로 확인 안 되는 것, 어긋나는 서술, 외부 확인이 필요한 것
  coverage.md        수집과 반영 점검표, 반영하지 않은 페이지와 사유
  log.md             작업 기록(날짜, 수집 범위, 고친 것)
```

작성 규칙:
- 사실 한 줄마다 출처 URL을 붙인다: `- 내용 [출처](URL)`. 페이지 맨 위에 확인한 날짜를 적는다.
- 공식 사이트 내용은 "회사가 밝힌 내용"이다. 인허가, 규모, 순위처럼 제3자 확인이 필요한 주장은 그대로 사실로 쓰지 않고 open-questions.md에 확인할 곳(감독기관 등록부 등)과 함께 올린다.
- 사실과 해석을 섞지 않는다. 해석은 각 페이지 맨 아래 "해석" 절에 따로 둔다.
- 원문은 자기 말로 요약한다. 인용은 표현 자체가 중요할 때만 짧게 쓴다. raw 원문 묶음은 내부 작업용이고, 밖으로 나가는 산출물에는 요약과 출처 링크만 쓴다.
- 날짜가 있는 정보는 날짜를 함께 적는다. 사이트 안에서 서로 다른 숫자가 나오면 둘 다 적고 출처를 붙인다.

### 7. 누락 점검 (audit)

```bash
python3 scripts/sitewiki.py audit --work work/<회사> --wiki work/<회사>/wiki
```

`coverage.md`에 수집 대기, 차단, 오류, 내용 없음, 그리고 "정독했으나 위키 어디에도 출처로 안 쓰인 페이지"가 나온다. 마지막 목록의 각 페이지는 위키에 반영하거나, wiki/coverage.md의 "읽었으나 반영하지 않은 페이지" 아래에 URL과 사유를 적는다. 이 목록이 0이 되어야 끝난 것이다. 계획이 list나 skip이라 안 읽은 범위는 구역과 쪽수를 coverage.md에 그대로 밝힌다.

### 8. 전달과 보관

- 위키 폴더와 `inventory.csv`, `coverage.md`를 전달한다. 프로젝트가 연결된 대화라면 위키 페이지를 프로젝트 문서로도 저장한다.
- 작업 폴더(장부와 raw)는 다음 대화로 넘어가지 않을 수 있다. 다시 쓸 일이 있으면 zip으로 묶어 사용자에게 준다.
- 나중에 갱신할 때는 이전 작업 폴더를 그대로 두고 map을 다시 실행한다. 새 URL만 대기 상태로 추가된다.

## 지킬 것

- robots.txt가 막은 경로는 수집하지 않는다(스크립트가 자동으로 뺀다). 로그인이 필요한 화면, 캡차, 차단은 우회하지 않는다.
- 요청 속도를 올리지 않는다(기본: 동시 4건, 묶음 사이 1초).
- 공개용이 아닌 호스트(staging, dev, test, internal, admin 등)는 열지 않는다.

## 막혔을 때

- 상태가 blocked인 페이지: WebFetch 같은 다른 정식 열람 도구로 그 URL만 다시 시도한다. 그래도 안 되면 coverage에 "미열람(차단)"으로 남기고, 필요하면 사용자에게 직접 열어 달라고 한다.
- 셸에서 사이트 접속 자체가 막힌 환경: 스크립트를 쓸 수 없다. 사용자 컴퓨터(Claude Code 등)에서 이 스크립트를 돌려 작업 폴더를 받아 오거나, robots.txt와 사이트맵을 웹 열람 도구로 읽어 같은 형식의 장부를 손으로 만들고 5단계부터 같은 방식으로 진행한다.
- 브라우저 실행 실패: `--render never`로 정적 수집만 먼저 하고, thin으로 남은 페이지만 따로 처리한다.
- 수집이 너무 오래 걸림: `plan`의 `--skim-cap`을 낮추고, 글 묶음은 핵심어로 걸러 올리는 방식으로 바꾼다.
